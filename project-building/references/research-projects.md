# 研究与长时间运行任务

仅在项目涉及实验设计、远程训练、批量评测或长时间运行时使用。具体预算、资源、评分和停止方式来自目标项目，不沿用示例项目的数字。

## 实验启动前

把实验要回答的问题写清楚：假设是什么、与谁比较、改变了什么、保持了什么、用什么指标判断。探索性实验允许设计未完全固定，但要如实记录，不能事后写成预先确定的确认性检验。

保存足以复现和解释结果的信息：代码版本或冻结副本、配置、数据与抽样方式、训练和评测种子、预算、环境、启动入口、结果目录。根据风险选择适当的版本标识，不为每个普通改动强制做全目录哈希。

模型或候选选择所用数据与最终测试分开。已查看并用于设计判断的测试证据要标注用途；重新命名或重新运行不会让它变成未见测试。

## 部署与运行

- 先确认实际运行入口和解释器，检查必要的磁盘、内存与并发资源；说明“作业数、每作业子进程数、训练轨迹和预算”的物理含义。
- 保留本次运行对应的源码、配置与日志。运行中会重新导入的共享源码不能随意覆盖；按项目方式使用冻结副本或独立部署目录。
- 启动后检查真实进程和首批有效产物，不能仅以启动命令返回成功宣称实验正常。
- 记录 run 标识、服务器路径、日志、停止与恢复入口。停止、重启与清理以用户授权和项目约定为准。
- 出现问题时，先定位到具体阶段和根因；修复明确适用哪条 run、是否影响旧产物，以及恢复后验证了什么。

## 检查进度

结合进程、日志和产物判断状态。区分“进程存在”“持续产出”“等待外部服务”“训练或考试完成”“整代汇总完成”。

代数、已测候选数、训练重复数分别报告；缓存复用不能当成新训练。失败、重试、缺失和未完成记录不能静默当成有效结果。

报告时间使用明确时区。只读查询只汇报，不顺手修改配置、恢复任务或更新文档；用户要求维护记录时再落盘。

## 分析与结论

先确认比较协议一致；不一致时写明差异，避免直接归因。将原始观测、统计汇总、解释假设和设计建议分开。

为分数保留重复、缺失与失败处理、基线、预算和汇总方式；结果链接到生成脚本和实际产物。图表或排名由对应脚本生成，不手改输出。

阶段记录应包括：问题与动机、实验条件、实际结果、支持的结论、限制、下一步。例如对训练配方的怀疑需要对照验证，不能仅凭一次冠军分数判断训练算法优劣。

重要中间实验和否定结果同样记入 PROGRESS，保存“为什么后来换了方案”的依据。独立的分析、审查或方案比较放在对应模块或版本的 guides/，其有效结论同步到 DESIGN 或 PROGRESS，README 提供入口；原始产物留在实验目录。最新全局状态写入 HANDOFF，避免重复维护完整结果。

# 笔记写作风格

本风格来自用户指定知识库中较成熟的 Agent、推理与命令行笔记：直接定义问题，按执行顺序解释，用最小例子展示输入和输出，并把资料链接放在正文附近。

## 1. 基本结构

简单概念：

```markdown
# 主题是什么

论文：[标题](URL)
官方文档：[标题](URL)

> [!abstract] 一句话理解
> 一句话定义。

## 关键点

- 具体事实 1
- 具体事实 2

## 最小示例

输入：...

```language
...
```

输出：...

## 限制

- ...

## 来源

- [标题](URL) — 发布者，访问于 YYYY-MM-DD
```

流程或 API：

```markdown
# 主题

一句话说明用途。

## 前置条件
## 输入
## 执行过程
## 输出
## 最小可运行示例
## 版本与弃用状态
## 常见错误
## 来源
```

只保留主题真正需要的章节。

## 2. 句子与段落

- 一段只解释一个结论。
- 先写结论，再写原因或证据。
- 使用“读取、传入、返回、缓存、更新、比较、验证”等具体动词。
- 主语不清时补出执行者，例如“运行时返回错误”，不要写“然后就会报错”。
- 避免“其实”“简单来说”“众所周知”“显而易见”等无信息词。
- 术语第一次出现时定义；不要为同一概念反复更名。

## 3. 输入、处理、输出

涉及程序、模型、协议或算法时，至少回答：

```text
输入：数据类型、形状/字段、单位、必要条件
处理：真正影响结果的步骤
输出：类型、形状/字段、含义、失败形式
```

如果数据会改变，说明在哪里改变；如果存在缓存、状态或副作用，明确指出。对 API、协议或模型调用，优先给出真实边界格式（例如完整请求 JSON 与关键响应字段），并明确由哪个组件生成和消费。

## 4. 代码与命令

- 示例应短，但不能使用未定义的关键变量或省略核心步骤。
- 命令前写运行位置和前置依赖。
- 命令后写预期输出或要观察的现象。
- 代码注释解释设计理由或不直观行为，不逐字复述语法。
- 不能运行的示例标记为“未运行验证”，并说明原因。
- 已弃用写法只能出现在迁移对照中，不能作为默认示例。

## 5. 表格、列表与公式

- 比较固定维度时使用表格。
- 有先后依赖时使用编号列表。
- 并列事实使用项目列表。
- 公式使用 LaTeX；公式后立即定义符号、单位和适用条件，并在有助于理解时给一组具体数值。
- 只有流程关系确实难以用几句话说清时才画图。
- 图片只能补充正文；移除图片后，文字仍应完整表达核心内容。

## 6. 引用

- 标题后先列本篇实际使用的 `论文：`、`官方文档：`、`官方仓库：` 或 `博客：` 链接，让资料范围立即可见。
- 定义、版本、参数、实验数字和弃用信息应就近引用。
- 一个引用只承担它实际支持的结论。
- 文末来源列表去重，并包含访问日期。
- 博客中的观点要标明作者或来源，不改写成行业共识。

## 7. 删除这些内容

- 比喻、拟人化和故事化铺垫；
- 与读者目标无关的完整历史；
- 宣传性形容词和没有指标的“更快”“更强”；
- 同一结论的多次复述；
- 为了版式完整而添加的空泛“总结”；
- 没有在正文中使用的链接；
- 资料未支持的细节补全。

## 8. 最终自检

交付前快速回答：

1. 读者能否在前两段知道主题是什么、解决什么问题？
2. 输入和输出是否具体到字段、类型、形状或可观察结果？
3. 示例是否对应当前推荐版本？
4. 每个时效性结论是否可追溯？
5. 删除比喻和背景后，正文是否仍完整？
6. 是否清楚标记推断、未验证项和适用范围？
